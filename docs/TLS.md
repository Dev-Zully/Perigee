# TLS and Certificate Management

Closes [#628](https://github.com/OdyxeeeLabs/Perigee/issues/628).

Perigee's web app is a Next.js frontend and `core/` is a Rust API. Both are
network-facing, and the API holds the off-chain records that
[encryption at rest](ENCRYPTION_AT_REST.md) protects — so plaintext in transit
would make that control decorative.

The deployed posture is declared in
[`config/security/tls-policy.yml`](../config/security/tls-policy.yml) and
enforced in CI by
[`scripts/security/verify_tls_config.py`](../scripts/security/verify_tls_config.py).

## External TLS 1.3

| Control | Setting |
| --- | --- |
| Minimum version | TLS 1.3 |
| External certificates | Let's Encrypt via cert-manager, auto-renewed |
| Renewal window | 30 days before expiry |
| Expiry alerting | 30 / 14 / 7 / 1 days |
| HSTS | `max-age=31536000; includeSubDomains; preload` (see [SECURITY_HEADERS.md](SECURITY_HEADERS.md)) |

TLS 1.2 is **not** offered. That is a deliberate compatibility cost: the
Perigee frontend and `core/` are both under our control, and every browser
Perigee supports negotiates 1.3. Offering 1.2 "for compatibility" with clients we
do not have is how cipher suites accumulate until nobody can remember why any of
them are still there.

### Cipher suites

TLS 1.3 fixes its own suite list, which is the point of the version:

```
TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
```

TLS 1.2 suites, if a future client forces 1.2, are restricted to forward-secret
AEAD only — no CBC, no RSA key exchange, no compression:

```
ECDHE-ECDSA-AES128-GCM-SHA256
ECDHE-RSA-AES128-GCM-SHA256
ECDHE-ECDSA-AES256-GCM-SHA384
ECDHE-RSA-AES256-GCM-SHA384
```

`TLS_FALLBACK_SCSV` is sent so a downgrade attempt is logged rather than
silently accepted.

## Internal mTLS

Service-to-service traffic inside the cluster terminates TLS with client
certificates from SPIRE, which issues short-lived SVIDs from the node's own
identity rather than from a long-lived certificate an attacker could exfiltrate.
Linkerd enforces this between services.

mTLS is what stops a compromised pod from calling `core/` directly. Without it,
network policy is the only control between a compromised workload and the API's
database — and network policy is a firewall rule someone will eventually widen.

## Verification

### Automated, in CI

```bash
python3 scripts/security/verify_tls_config.py
testssl.sh --quiet --warnings off https://staging.perigee.example
```

`testssl.sh` is what actually answers "is TLS 1.3 with only modern ciphers
served", because it inspects the wire rather than the configuration.

### Manual, before each release

```bash
# Protocol versions offered
openssl s_client -tls1_2 -connect perigee.example </dev/null   # must fail
openssl s_client -tls1_3 -connect perigee.example </dev/null   # must succeed

# Certificate identity and expiry
openssl s_client -connect perigee.example </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

The first command failing is the check that matters. A server that still answers
1.2 will answer it regardless of what the config says.

## Certificate lifecycle

cert-manager renews automatically. What automation does *not* do is notice when
renewal has silently stopped, so:

- **Alerting at 30 / 14 / 7 / 1 days.** 30 days is early on purpose: it is the
  renewal window, so an alert at 30 days means renewal is not happening *now*,
  not that there is an emergency.
- **Synthetic TLS probe** every 5 minutes from outside the cluster, because an
  alert generated by the same system that manages the certificates cannot tell
  you the certificate system is down.
- **The renewal window is 30 days, not 7.** Combined with 90-day certificate
  lifetimes that gives two chances to renew before expiry. cert-manager issues
  at one third of remaining lifetime, which lands comfortably inside that.

## Preload

`preload` in the HSTS header is only a request — the browser ignores it until the
domain is submitted to the preload list. That is an operational step, not a code
change, and it is irreversible for the browser population that has already
preloaded: every subdomain must be HTTPS-capable first. Sequence it after the
internal mTLS rollout.

## Adding a hostname

1. Add it to `external_domains` in `config/security/tls-policy.yml`, with an
   expiry-monitoring entry.
2. Confirm every hostname resolves before adding `includeSubDomains`, not after.
3. Only submit to the preload list once *all* subdomains are live.
